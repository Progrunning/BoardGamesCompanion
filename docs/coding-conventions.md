# Coding Conventions

How code is written in this repo's two live codebases: the .NET backend (`backend/`) and the Flutter app (`board_games_companion/`). Mechanical style (formatting, whitespace, most lint rules) is enforced by each codebase's own config — this doc covers the patterns those configs don't catch: architecture, naming, DI, and testing conventions to follow when writing new code.

`cloud_infrastructure/` and `pipelines/` are the legacy Azure estate being retired (see `docs/adr/0001-hetzner-blue-green-deploy.md`) and aren't covered here.

## Backend (`backend/`) — .NET / C#

Mechanical style: `backend/.editorconfig`, `backend/Directory.Build.props` (target `net9.0`, `Nullable` enabled, `ImplicitUsings` enabled). Test projects implicitly reference `AutoFixture`, `Xunit`, `Moq`, `Moq.Protected`, `MongoDB.Driver`, `FluentAssertions`, `Microsoft.Extensions.Logging`.

- **Layering**: Endpoint → Service → Repository / external-client Service. `BGC.SearchApi` is a minimal-API host — endpoints are declared inline in `Program.cs`, there's no `Controllers/` folder. `BGC.Core` holds cross-cutting domain logic used by both the API and the cache worker: `Models/Domain`, `Models/Dtos`, `Models/Settings`, `Models/Exceptions`, `Repositories/` (+ `Repositories/Interfaces/`), `Services/` (+ `Services/Interfaces/`).
- **Dependency injection**: constructor injection, one interface per class, interfaces live in a sibling `Interfaces/` folder. `BGC.Core.Extensions.ServiceConnectionExtensions.AddCoreServices` centralizes Core's registrations (typed `HttpClient` + Polly retry policy per external service); `Program.cs` layers on API-specific registrations. Most services are `Transient`; `ICacheService` is `Singleton`. Config uses the options pattern everywhere — `AddOptions<T>().Configure<IConfiguration>(...).ValidateDataAnnotations().ValidateOnStart()`.
- **Naming**: classes are `XyzService` / `XyzRepository`; interfaces are `IXyz`. Private fields are `_camelCase`. Async methods do **not** get an `Async` suffix (`Search`, `GetBoardGames`, not `SearchAsync`). Domain models and settings are `record` types with `init`-only properties; services and exceptions are `class`.
- **Testing**: test classes are `<ClassUnderTest>Tests`; test methods follow `MethodName_Scenario_ExpectedResult`. Set up mocks as `Mock<T>` fields in the constructor, instantiate the class under test as a field/local. FluentAssertions for all assertions. AutoFixture is used ad hoc (not everywhere) to generate DTOs. Shared cross-project test helpers (e.g. `HttpClientHelpers` for faking `HttpClient` via `Mock<HttpMessageHandler>` + `Moq.Protected`) live in `BGC.Tests.Core`. No shared abstract test base class — each test class is self-contained.
- **Errors & logging**: domain-specific exceptions derive from `Exception` with minimal custom state (`BggException`, `XmlParsingException`), thrown at service boundaries. Centralized handling via `app.UseExceptionHandler("/api/error")` → `IErrorService.HandleError`, which pattern-matches exception type and returns `Results.Problem` / `Results.StatusCode`. Structured logging via `ILogger<T>`; Serilog with a bootstrap logger + OpenTelemetry sink.
- **API conventions**: minimal APIs only, lower-case routes (`api/search`), `[Authorize]` on the delegate, `[FromQuery]` binding, `CancellationToken` passed through explicitly. Swagger via `WithOpenApi()`. No API versioning.
- **Data**: MongoDB domain models use `[BsonId]` / `[BsonElement]` / `[BsonRequired]` / `[BsonRepresentation]` attributes on record properties. Constants are centralized in per-project `Constants.cs` as nested static classes.

## Flutter app (`board_games_companion/`) — Dart

Mechanical style: `board_games_companion/analysis_options.yaml` (built on `flutter_lints`, plus `strict-casts`/`strict-raw-types`, `prefer_single_quotes`, `prefer_const_constructors`, `prefer_final_locals`/`prefer_final_fields`, `always_declare_return_types`, and more).

- **Architecture**: layer-first `lib/` — `pages/`, `widgets/`, `stores/`, `services/`, `models/` (with `api/`, `bgg/`, `hive/`, `navigation/`, `results/` subfolders), `common/`, `extensions/`, `mixins/`, `utilities/`. Each `pages/<feature>/` folder pairs a page widget with a co-located `<feature>_view_model.dart`.
- **State management**: MobX throughout. Page-level `*ViewModel` classes and cross-cutting `*Store` classes both follow the `abstract class _XBase with Store { ... }` / `class X = _XBase with _$X` codegen split, with `@observable`/`@computed`/`@action` and `reaction(...)` for side effects. UI observes state via `flutter_mobx`'s `Observer(builder: ...)` and calls view-model methods directly.
- **Dependency injection**: `get_it` + `injectable`. Classes register via `@injectable` / `@singleton` annotations on the concrete class. Manual or third-party construction goes through an `@module abstract class RegisterModule` with `@singleton`/`@injectable` getters. The generated `injectable.config.dart` is wired up in `lib/injectable.dart` and excluded from lint.
- **Naming**: files are snake_case matching their primary class (`home_view_model.dart`). Generated files use `.g.dart` (mobx/hive/json_serializable) or `.freezed.dart` suffixes. MobX base/impl classes split as `_XViewModelBase`/`XViewModel` or `_XStoreBase`/`XStore`. Mocks live in `test/mocks/<snake_case>_mock.dart`. Private members are `_`-prefixed.
- **Widgets**: pages are typically `StatefulWidget`s (`<Page>State`) even when rendering is mostly delegated to `Observer`. Many pages extend the shared `BasePageState<T extends StatefulWidget>` for common behavior. View models and dependencies are passed into page constructors rather than looked up inside child widgets. Reusable UI lives under `lib/widgets/<area>/`.
- **Testing**: `test/` mirrors `lib/` by category (`view_models/`, `services/`, `pages/`, `models/`, `extensions/`), plus a shared `test/mocks/` directory of hand-written `mocktail` mocks (`class MockX extends Mock implements X {}` — the project uses `mocktail`, not `mockito`). Test naming is BDD-style with nested strings: `group('GIVEN ...', () { test('WHEN ... THEN ...', () {...}); })`. No golden tests.
- **Models**: result/union-type models use `freezed` with `const factory` constructors. Persisted domain models combine `freezed` + `hive`, annotating fields with `@HiveType(typeId: ...)`/`@HiveField(n)` inside the freezed factory — `HiveField` indices and `HiveBoxes` type IDs must stay stable once assigned. API DTOs use `json_serializable`.
- **Other**: logging via `Fimber` (`Fimber.d`/`Fimber.e`), not `print`. Fire-and-forget async calls are explicitly wrapped in `unawaited(...)`. Analytics events are centralized in an `Analytics` constants class and logged through an injected `AnalyticsService`.
