# Replace Hive with SQLite via drift, staged through hive_ce

`hive` 2.2.3 was last published four years ago, its 4.0 line has sat in prerelease since, and its author now redirects users to Isar — which has itself stalled. The app keeps all eight of its boxes in this format, so the abandonment is a standing risk to data nobody can re-create. We are moving persistence to SQLite behind [drift](https://pub.dev/packages/drift), in two independently shippable stages: first a drop-in swap to the maintained `hive_ce` fork, then a one-shot migration of every box into a relational schema.

The maintenance risk alone would not justify this. `hive_ce` answers it for about a day of work. The move to SQLite is justified by two pains `hive_ce` cannot fix — **no transactions across boxes** (a playthrough, its scores, and its players are written to three boxes with nothing making that atomic) and **whole-collection residency in RAM** (every box is a `Box`, not a `LazyBox`, and the MobX stores hold a second copy) — and by the fact that SQLite's durability guarantee is structural rather than social: a `.db` file survives the death of any package that reads it, which `.hive` never could.

## Status

accepted — stage 1 (`hive_ce`) and stage 2 (SQLite) ship as separate releases.

## Consequences

- **The Hive dependency does not go away.** App stores only install the newest build, so a user updating from a 2024 version lands directly on whatever ships in 2027 and must still find a working Hive reader there. More binding: `FileService` backups are zips of raw `*.hive` files, and those zips sit in users' Google Drives indefinitely. As long as Restore accepts them, the app carries a **legacy store** reader. This is the whole reason stage 1 exists — the reader we are stuck with for years should be one someone is still patching.
- **The migration triggers on the presence of `.hive` files, not on a version flag.** Restoring a pre-migration backup therefore reuses the migration path rather than needing its own. Restore means replace, so `.hive` present must win over an existing `.db`: delete the database and re-migrate. The inverse rule would make restore silently do nothing.
- **Migration is eager, one-shot, at launch, off the UI isolate.** It writes a new database and swaps it in only after verification passes. `.hive` files are never deleted — they are the rollback, the evidence for bug reports, and the input to a second attempt.
- **Failure is closed, not fatal.** Verification failure discards the new database, leaves the app running on Hive, and reports to Crashlytics, with a ceiling on retries. A user still on Hive is fine; a user in a launch crash-loop uninstalls.
- **Verification is proportional to replaceability.** Row counts and referential invariants for everything; full round-trip equality — free from freezed's generated `==` — for **user-authored data**. **Catalogue data** gets counts only, because BGG can regenerate it.
- **The migration is lossless, with one carve-out.** Every Hive field gets a column, including the `@Deprecated` `Score.value` (as `legacy_value`, since a score recorded only there is a real result). The exception is `Playthrough.scoreIds`, which is provably reconstructible from the `scores` foreign key and whose removal is itself verifiable. Cleanup of dead fields happens later, as separate schema migrations with telemetry behind them.
- **`BoardGameDetails` splits into two tables.** `board_games` holds **catalogue data**; `collection_entries` holds the **collection entry** (`isOwned`, `isOnWishlist`, `isFriends`, `isBggSynced`, `isCreatedByUser`, `settings`). Today `BoardGamesStore.refreshBoardGameDetails` preserves those fields through a hand-maintained `copyWith` list, guarded only by a doc comment on the model warning future editors to update it — add a user-owned field, forget the line, and refresh silently wipes it. After the split, refresh cannot reach `collection_entries` at all. The comment and the `copyWith` list are deleted.
- **Nested catalogue lists become child tables keyed by `board_game_id`, not a shared catalogue.** BGG owns them and replaces them wholesale per game, so refresh is a delete-then-insert with no orphans and no reconciliation. Two carve-outs: `expansions` becomes a self-referencing link table with a real foreign key (the relation is already implicit in `refreshBoardGameDetails` auto-inserting each expansion as a game), and `settings` lands on `collection_entries` because it is the user's configuration, not BGG's.
- **Enums are stored by name, not by index.** Hive persists enums as `@HiveField` positions, so reordering a Dart enum silently corrupts existing rows. Names cost a few bytes and are readable when debugging a restored backup.
- **Settings stay inside SQLite.** `user` and `collectionFilters` become single-row tables; `preferences` becomes a `(key, value)` table with JSON-encoded values, preserving `PreferencesService`'s typed accessors verbatim. Moving them to `shared_preferences` would take them out of the documents directory and therefore out of backups — which, since `firstTimeLaunchDate` and `rateAndReviewDialogSeen` drive the review prompt, would nag users after every restore. Behaviour is held constant.
- **Backups gain a manifest and must gain an extension.** `FileService.backupFileExtensions` is a whitelist; unless `.db` is added **in the same commit** as the drift write path, backups silently become image-only archives. A `manifest.json` carrying schema and app version lets a restore of a newer backup onto an older install fail with a message instead of handing drift a schema it cannot open. (`restoreAppData` also returns `false` on success and `true` on cancel — an inversion worth fixing while the file is open.)
- **The SQLite release ships no memory improvement, deliberately.** Service signatures are unchanged, so the stores still call `retrieveBoardGames()` and still hold everything. SQL is the *enabler* for fixing memory, not the fix: replacing `ObservableList<BoardGameDetails> allBoardGames` with a lightweight projection is the immediately following project, and it is a safe refactor precisely because no data is at stake by then.
- **drift is confined to `services/`.** Freezed domain models are kept for all 26 types with hand-written mappers at the service boundary, so stores, view models, pages, and the 29 existing tests compile untouched and act as the migration's safety net. Assembling `BoardGameDetails` from ~9 tables is the largest and most bug-prone chunk of the work; that is an argument for testing it hard, not for a different design.
- **`docs/coding-conventions.md` goes stale at stage 2.** Line 23 lists `models/hive/` in the architecture and line 29 encodes the Hive modelling rule about stable `HiveField` indices and `HiveBoxes` type IDs. Both need rewriting when the schema lands — not at stage 1.

## Considered options

- **Swap to `hive_ce` and stop there** (rejected as an endpoint, adopted as stage 1: it retires the maintenance risk for a day's work but leaves cross-box writes non-atomic and the whole collection in RAM, and it keeps the data in a format only one package on earth can read)
- **Stay on `hive` 2.2.3 and go straight to SQLite** (rejected: bets the entire multi-week migration landing before a Dart or Flutter release breaks an unpatchable dependency, and leaves a dead package as the permanent legacy reader)
- **sqflite with hand-written SQL** (rejected: thinner dependency, but hand-rolled migrations and hand-written mapping for 26 types, with no build-time verification of either. drift's codegen produces SQL against a standard file, not a proprietary format — a different risk from the one Hive's codegen carried)
- **Let drift own the domain types, via generated data classes or `@UseRowClass`** (rejected: the aggregate roots are not rows — `BoardGameDetails` spans ~9 tables and `Playthrough` spans 3 — so it would only work for the three flat leaf models, and it would put a package back in charge of the model layer)
- **Migrate lazily, per box on first access** (rejected: months of "which store am I reading?" branching across nine services, and bugs reachable only by users stranded in a half-migrated state)
- **Dual-write to Hive and SQLite during a coexistence period** (rejected: two sources of truth and reconciliation logic, which is more dangerous than the problem it hedges)
- **Rework the read path in the same release** (rejected: changing the storage engine and the access architecture at once against irreplaceable data means that when something is wrong, nothing tells you which half did it — and it discards the existing tests as a safety net at the exact moment they are worth most)
- **Fully normalize categories, publishers, designers, and artists into shared catalogue tables** (rejected: nothing queries across them — `CollectionFilters` has three fields and no store touches them — so it buys upsert-plus-orphan-collection complexity on every refresh in exchange for deduplicating a few thousand short rows)
- **Store nested lists as JSON columns** (rejected: smallest diff, but it is document thinking in SQL clothing and forecloses the projection work that fixes memory)
- **Split `board_games` from `collection_entries` later, as a follow-up migration** (rejected: a second schema migration over live user data, when the split is nearly free inside a migration already being written)
- **Clean up deprecated fields during the migration** (rejected: every intentional difference becomes an exception the verification must encode, and exceptions are where "intentional" quietly becomes "accidental")
