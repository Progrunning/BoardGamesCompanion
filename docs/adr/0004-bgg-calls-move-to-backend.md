# Move BGG XML API calls from the Flutter client to the backend

Today only `/xmlapi2/search` is backend-mediated (via the Search API's `BggService`); `/hot`, `/thing`, `/collection`, and `/plays` are called directly from the Flutter client, each install carrying its own compile-time BGG API key. This means BGG rate limits are governed by install count rather than by us, response caching resets per device instead of being shared, and there is no way to demonstrate compliance with BGG's XML API terms around unnecessary calls. We are extending the Search API to front all four remaining endpoints, in two phases: `/hot` and `/thing` first (catalogue data, cacheable), `/collection` and `/plays` second (BGG-username-scoped, proxied but not persisted). New app builds call the Hetzner backend directly with a new shared API key; legacy installs keep calling BGG directly, unchanged, for the same reason ADR-0002 could not repoint them.

## Status

accepted — phase 1 (`/hot`, `/thing`) ships before phase 2 (`/collection`, `/plays`). Implementation waits on the Hetzner migration PR referenced in ADR-0001 landing.

## Consequences

- **BGG rate-limit exposure moves from per-install to per-deployment.** A single shared `BggSettings.ApiKey` on the backend replaces one key per app install. This is the entire point — it's the only way to make "how many calls does BGG see" a number we control rather than a number that scales with our install base.
- **Legacy installs are permanently out of scope, not temporarily.** Same constraint as ADR-0002: base URLs and keys are baked into shipped binaries with no forced-update path, so pre-migration installs keep calling `boardgamegeek.com` directly forever. Unlike ADR-0002, no shim is being built to catch them — collections, plays, game details, and hot games staying client-side for old installs is an accepted permanent gap, not a bridge to something else.
- **New endpoints bypass APIM entirely.** ADR-0002 established APIM as a legacy-only shim for `/search`; extending it to four more endpoints would make Azure load-bearing for traffic that has no legacy constraint. New builds authenticate straight to Hetzner with a new shared static key via the existing `ApiKeyAuthenticationHandler` scheme — there is no per-user identity to carry (the app has no login system; a BGG username is a client-supplied string, not an account).
- **`/hot` and `/thing` get different cache-refresh mechanisms, deliberately.** `/thing` is keyed by board game id and reuses the existing Mongo cache + Service Bus stale-refresh worker unchanged (7-day TTL, same as today's client cache). `/hot` is a single global list with nothing to key a per-item staleness check against, so it gets a plain read-through cache instead: a request finding the cached document stale (24h TTL, same as today) triggers a synchronous BGG fetch and overwrite. No worker or timer is introduced for `/hot` — a second refresh mechanism for one document was judged not worth the operational surface.
- **Hot-list history sampling is lossy by design.** Every `/hot` rehydration also writes a deduped daily snapshot (game id, rank, timestamp) to a separate append-only collection, retained one year on a rolling expiry, intended for future rank-trend display. Because sampling is tied to lazy rehydration rather than a clock, a day with zero requests after the cache goes stale produces no snapshot for that day. This is an accepted gap, not a bug to fix later — closing it means adding the scheduled worker `/hot` deliberately avoided.
- **`/collection` and `/plays` stay unpersisted, per the existing catalogue-data/user-authored-data boundary.** BGG's collection export API returns HTTP 202 while a requested export is being prepared; the client currently polls this itself. The backend now absorbs that polling internally, bounded by a timeout, and returns a distinct "still processing" response (not a generic error) if the bound is hit before BGG finishes — the client's existing retry/backoff logic keeps working against the backend instead of BGG, without collapsing "still working" into the same path as "actually failed."
- **Response bodies become JSON DTOs, matching `/api/search`.** The Flutter client's XML parsers for collection and plays (currently run via `compute()`) are retired for migrated traffic; XML parsing exists only inside the backend now.

## Considered options

- **Extend the APIM shim to all four endpoints** (rejected: makes Azure permanently load-bearing for endpoints with no legacy-client constraint, and blurs the shim's single job established in ADR-0002)
- **Give `/hot` the same per-id Service Bus worker pattern as `/thing`** (rejected: `/hot` has no natural per-item key to check staleness against — it is one list, not N independent records — so the pattern would be forced onto data it doesn't fit)
- **Guarantee daily hot-list history with a scheduled snapshot job** (rejected for now: buys a stronger guarantee at the cost of the exact kind of standalone worker `/hot`'s caching was designed to avoid; revisit if the trend feature turns out to need gap-free history)
- **Forward BGG's 202 straight to the client instead of absorbing it in the backend** (rejected: keeps BGG's async queuing model as part of the public contract for no benefit, when the backend can hide it the same way it already hides Polly retries for `/thing`)
- **Persist `/collection` and `/plays` results server-side** (rejected: these are user-authored/BGG-account-scoped, not catalogue data; persisting them server-side would create a second copy of data that CONTEXT.md already places in the user-authored-data boundary, owned by the client's SQLite store)
